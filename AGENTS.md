# Agent entry point

**This is the shared instruction entry point for Codex, Claude, OpenCode and other agent harnesses.**

**Read [MASTER_PLAN.md](MASTER_PLAN.md) before doing project work.** It is the single authoritative source for the project goal, scope, architecture, ordered milestones, current progress, evidence, operator commands and engineering rules. New human instructions take precedence.

**Any stateless Codex, OpenCode or other agent starts with the master's “Stateless startup and mid-flight recovery” procedure and shared live work record.** Check `uv run globe review inbox` for new human answers, read [HUMAN_REVIEW.md](HUMAN_REVIEW.md) for operator/archive guidance, and read recent [CHANGELOG.md](CHANGELOG.md) entries before choosing work. Do not depend on chat history or another harness's terminal IDs. Inspect actual processes and durable results, record ownership/checkpoints, and keep P0—the still-open value of further OCR cleanup—part of the active plan.

- The review desk is an intentionally unauthenticated, single-user local-network tool, as explicitly requested by the human on2026-10-24. Do not reintroduce access codes/auth unless the human requests a changed deployment scope.
- Human reviews use the Streamlit desk (`make review`) and SQLite. At every startup run `uv run globe review inbox`, then inspect relevant archived answers and the master HR register before choosing work. `HUMAN_REVIEW.md` is an operator/archive pointer, not an editable queue. Never fabricate a human submission or edit the database directly.
- Author immutable versioned JSON packets using `uv run globe review schema` and `review register PACKET.json`; keep the packet in tracked `docs/review-packets/`. Blind packets must omit model outputs/recommendations from all text/evidence. Include exact source IDs/hashes/citations in evidence labels and context. Notify the human of a concrete ready packet. New question content requires a new version; synthetic DEMO packets never become research labels or policy.
- Consume browser submissions without requiring a separate chat notification: use `review export SUBMISSION_ID --output docs/archive/human-review/<HR-ID-version>/<submission-id>.json`, verify the packet/answer hashes and revision order, apply answers narrowly to `MASTER_PLAN.md`, and commit the plan plus exact archive. Then `review applied SUBMISSION_ID --reference COMMIT` and export the receipt to a separate new JSON path; commit that receipt. Do not overwrite exports or mark applied before the plan/archive commit exists. Preserve earlier revisions, inspect supersession, and never let an older answer override a later revision. The inbox contains the latest unapplied revision per reviewer; superseded versions stay in export/history and cannot be marked applied. Legacy Markdown answers/chat responses retain the existing exact-byte archive/receipt procedure; HR-005/008 originals stay immutable. No silent free-text conversion to validated subject labels or expanded approval.
- Follow the master's H1–H6 human checkpoints and shared HR register. Explicitly tag the human with a concrete packet when a decision or sample grade is needed; record actual requests/answers and blocking scope. Never treat AI review or silence as human approval. Reuse existing authorization and keep independent work moving instead of asking permission for routine tasks.
- Advance its current milestone and next decision; check actual files, Git and run state before acting.
- Update the master plan’s current status, milestone/evidence tables and next action in place after each unit and before handoff. Append one compact dated history entry to [CHANGELOG.md](CHANGELOG.md); historical entries belong there, not at the bottom of the master plan. Do not create another plan, progress file or competing backlog.
- `PROGRESS.md`, `PROJECT_GOAL.md`, `V2_*`, `RUNBOOK.md`, `HAPPY_PATH.md` and `TAG_ARM_PROMPT.md` are compatibility pointers. Their archived originals are historical evidence, not current instructions or commands to execute.
- Preserve immutable sources, accepted ledgers and prior experiments. Keep bounded POCs separate from human-launched full workloads. Use Luna delegates for bounded preparation/review when available, following the master plan.
- Use uv and Pydantic v2; preserve source evidence and uncertainty. Keep Ollama sequential, inspect existing workers/queues and never expose secrets.
- Follow the master's validation/formatting rules, including `make gate` before code handoff, complexity≤5, and elevated `npx prettier@3.9.10 --prose-wrap never --write "**/*.md"` for Markdown edits when using Codex.
- Commit completed units with a single-line message ending in a brief identifier of the AI model making the commit, for example `Describe the change [model: GPT-6.1 Sol]`. Use the actual known model name; if unavailable, write `[model: unknown]` rather than guessing. Do not touch the separate investigation in `tmp/performance/`.

`README.md` is a short human tutorial, not a second project plan. The original documents are preserved under `docs/archive/2026-10-22-pre-masterplan/`; their original hashes are in its `manifest.json`.
